\section{Objectif}
% ==============================================================================

Implémenter un \textbf{tas max} en C++ (\texttt{src/10\_tas\_max.cpp}), y insérer les
valeurs d'un fichier (200\,000, 1\,000\,000 puis 10\,000\,000 valeurs), puis mesurer le temps
et le nombre d'échanges de trois opérations sur le tas construit :
\textbf{extraire le maximum une fois} (retirer la racine, puis réorganiser le tas),
\textbf{insérer une valeur qui reste à la fin} (aucune réorganisation) et
\textbf{insérer une valeur qui remonte jusqu'à la racine} (vérifiée à chaque niveau).
Puis comparer avec le tas de la STL, \texttt{std::priority\_queue}.

\section{Un arbre rangé dans un tableau}
% ==============================================================================

Un tas max est un arbre binaire \textbf{complet} (rempli niveau par niveau, de gauche à
droite) qui respecte une seule règle : \textbf{chaque parent est plus grand que ses
enfants}. Le maximum est donc toujours à la racine.

Comme l'arbre est complet, on le range dans un simple \texttt{vector<int>}, sans pointeurs.
Pour la case $i$ :

\begin{center}
\begin{tabular}{l l}
parent        & $(i - 1) / 2$ \\
enfant gauche & $2i + 1$ \\
enfant droit  & $2i + 2$ \\
\end{tabular}
\end{center}

\section{Insertion : on ajoute en bas, puis on remonte}
% ==============================================================================

\begin{lstlisting}[caption={Insertion (\texttt{inserer} et \texttt{monter}).}]
// Insertion : ajoute la valeur dans la premiere case libre (a la fin),
// puis la fait remonter. O(log n).
void inserer(int val) {
    tas.push_back(val);
    monter(tas.size() - 1);
}

// Fait remonter la case i : tant qu'elle est plus grande que son parent,
// on les echange. S'arrete a la racine ou quand le parent est plus grand.
void monter(int i) {
    while (i > 0 && tas[(i - 1) / 2] < tas[i]) {
        swap(tas[i], tas[(i - 1) / 2]);
        echanges++;
        i = (i - 1) / 2;
    }
}
\end{lstlisting}

La nouvelle valeur est placée dans la première case libre (à la fin du tableau). Tant
qu'elle est plus grande que son parent, on les \textbf{échange} : elle remonte d'un
niveau. Elle s'arrête quand son parent est plus grand, ou à la racine.

Exemple : on insère dans l'ordre $10, 4, 15, 20, 8, 30$. Voici l'insertion de \textbf{20}
dans le tas $[15, 4, 10]$ (en vert la valeur qui remonte, en orange la case comparée, en
rouge l'échange) :

Une insertion a donc un \textbf{meilleur cas} et un \textbf{pire cas}, que le programme
mesure tous les deux une fois le tas construit :
\begin{itemize}
  \item \textbf{la valeur reste à la fin} (comme 8 ci-dessus) : elle est plus petite que
        son parent, une seule comparaison suffit, \textbf{0 échange}, $O(1)$ ;
  \item \textbf{la valeur remonte jusqu'à la racine} (comme 30) : elle est plus grande que
        toutes les autres, il faut la vérifier et l'échanger à chaque niveau,
        \textbf{$\log_2 n$ échanges} (17 pour 200\,000 valeurs), $O(\log n)$.
\end{itemize}
Les $n$ insertions du fichier coûtent donc au pire $O(n \log n)$.

\section{Extraction : on retire la racine, puis on redescend}
% ==============================================================================

\begin{lstlisting}[caption={Extraction du maximum (\texttt{extraireMax} et \texttt{descendre}).}]
// Extraction : retire et renvoie la racine (le max). Le dernier element
// prend sa place, puis on l'ajuste en le faisant descendre. O(log n).
int extraireMax() {
    int racine = tas[0];
    tas[0] = tas.back();
    tas.pop_back();
    if (!tas.empty()) descendre(0);
    return racine;
}

// Fait descendre la case i : on l'echange avec le plus grand de ses deux
// enfants tant qu'il est plus grand qu'elle. S'arrete quand elle est a sa
// place ou qu'elle n'a plus d'enfant.
void descendre(int i) {
    int n = tas.size();
    while (true) {
        int max = i;
        int g = 2 * i + 1;
        int d = 2 * i + 2;
        if (g < n && tas[g] > tas[max]) max = g;
        if (d < n && tas[d] > tas[max]) max = d;
        if (max == i) return;
        swap(tas[i], tas[max]);
        echanges++;
        i = max;
    }
}
\end{lstlisting}

Le maximum est la racine. Pour ne pas laisser de trou, on met le \textbf{dernier} élément
à la racine et on raccourcit le tableau. Cet élément est petit, donc la règle n'est plus
respectée : on l'\textbf{ajuste} en l'échangeant avec le plus grand de ses deux enfants,
jusqu'à ce qu'il soit plus grand que ses enfants ou qu'il n'en ait plus.

puis fait les deux insertions (reste à la fin, jusqu'à la racine).

\section{Résultats : notre tas et \texttt{std::priority\_queue}}
% ==============================================================================

La STL fournit déjà un tas max, \texttt{std::priority\_queue<int>} : un tas dans un
\texttt{vector}, avec \texttt{push(v)}, \texttt{top()} et \texttt{pop()} à la place de
\texttt{inserer(v)}, \texttt{max()} et \texttt{extraireMax()}. Le programme 11 mesure les
deux versions l'une après l'autre, sur les mêmes valeurs ; le programme 10 compte en plus
les échanges de notre tas.

Machine : Intel Core i5-1135G7 (cache L3 de 8~Mo), Linux, \texttt{g++} 15.2,
\texttt{-O3}. Trois fichiers de valeurs triées ($3, 6, 9, \dots$) : 200\,000, 1\,000\,000 et
10\,000\,000 valeurs (ce dernier, 86~Mo, est créé par \texttt{make data}). Chaque fichier est
testé dans son ordre (trié), puis mélangé.

\textbf{Ce qu'on en retient.}
\begin{itemize}
  \item \textbf{Insérer les $n$ valeurs : notre tas gagne}, sur les trois tailles. Sur le
        fichier trié il est 1,4 fois plus rapide à chaque exécution (707 contre 990~ms à
        10\,000\,000) ; sur les valeurs mélangées, de 6 à 8\,\% seulement.
  \item \textbf{Le fichier trié est le pire cas} : chaque valeur remonte jusqu'à la racine
        (213 millions d'échanges pour 10\,000\,000 valeurs, contre 13 millions mélangées).
        Avec plus de données, cela se voit : trié est 1,6 fois plus lent que mélangé à
        10\,000\,000 valeurs, probablement parce que le tableau (40~Mo) ne tient plus dans le
        cache du processeur.
  \item \textbf{Une seule opération : moins d'une microseconde, égalité.} Insérer une valeur
        qui reste à la fin ne fait \textbf{aucun échange} ; une valeur qui monte jusqu'à la
        racine en fait $\log_2 n$ (17 à 23), et une extraction 16 à 22. Multiplier $n$ par 50
        n'ajoute que 6 échanges : c'est le $O(\log n)$. Ces mesures sont si courtes qu'elles
        varient d'une exécution à l'autre, et aucune version ne gagne nettement.
  \item \textbf{Avec \texttt{-O3}, \texttt{priority\_queue} n'est donc pas meilleure
        partout} : elle ne gagne nettement aucune mesure. Mais ce classement dépend de
        l'optimiseur du compilateur (ci-dessous).
\end{itemize}

\subsection*{L'optimiseur du compilateur change le classement}

Tous les résultats ci-dessus sont compilés avec \texttt{-O3} (le \texttt{Makefile}) : le
compilateur \textbf{optimise} le code avant de l'exécuter. Compilé sans option
(\texttt{g++ fichier.cpp}, soit \texttt{-O0}), le même programme 11 donne un classement
\textbf{inverse} :

\begin{itemize}
  \item \textbf{Sans optimisation, \texttt{priority\_queue} gagne} : elle insère les valeurs
        triées \textbf{1,9 fois plus vite}, et gagne aussi l'extraction et l'insertion
        jusqu'à la racine. Notre code exécute alors chaque ligne telle quelle : un
        \texttt{swap} complet (3 copies) et plusieurs accès \texttt{tas[...]} à chaque niveau.
        \texttt{priority\_queue} déplace un \og trou \fg{} et ne copie qu'une valeur par
        niveau : elle fait moins de travail.
  \item \textbf{Avec \texttt{-O3}, l'optimiseur réécrit notre code} : il supprime les appels de
        fonction, garde les valeurs dans les registres du processeur, et notre \texttt{swap}
        devient aussi léger que le \og trou \fg{}. L'avantage de \texttt{priority\_queue}
        disparaît, et notre boucle, simple et écrite pour des \texttt{int}, finit même par
        être plus rapide sur le fichier trié (cause exacte non identifiée).
  \item L'optimisation rend tout \textbf{4 à 19 fois plus rapide} (802 $\to$ 42~ms pour notre
        tas). Comparer deux versions n'a donc de sens qu'avec les \textbf{mêmes options de
        compilation} : c'est ce qui explique que d'autres mesures, faites sans
        \texttt{-O3}, trouvent \texttt{priority\_queue} meilleure partout.
  \item En pratique, \texttt{priority\_queue} reste le bon choix : déjà écrite, testée, et
        rapide quelles que soient les options. Écrire notre tas permet de comprendre ce
        qu'elle fait et de compter les échanges.
\end{itemize}

\section{Conclusion}
% ==============================================================================

Le tas max se range dans un simple tableau : le parent de la case $i$ est la case
$(i-1)/2$. L'insertion fait \textbf{remonter} la nouvelle valeur, l'extraction fait
\textbf{redescendre} le dernier élément placé à la racine, et chacune coûte au plus la
hauteur de l'arbre, $\log_2 n$. Une insertion qui reste à la fin ne fait aucun échange ;
une insertion qui remonte jusqu'à la racine en fait $\log_2 n$ (23 pour 10\,000\,000
valeurs), en 0,1 à 0,2~$\mu$s. Insérer les $n$ valeurs prend environ 10~ms pour 200\,000 valeurs
et 0,45 à 0,7~s pour 10\,000\,000 ; des valeurs triées sont le pire cas, avec 12 à 17 fois plus
d'échanges, et l'écart de temps grandit avec $n$ (1,6 fois plus lent à 10\,000\,000).
\texttt{std::priority\_queue} est la version STL de la même structure. Le gagnant dépend de
l'optimiseur du compilateur : sans optimisation, \texttt{priority\_queue} est la plus rapide
(1,9 fois sur l'insertion des valeurs triées) ; avec \texttt{-O3}, notre tas la rattrape et la
dépasse pour insérer les $n$ valeurs.
